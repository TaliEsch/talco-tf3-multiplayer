# Code and bridge review — 16 September 2026

This review and implementation are incomplete. Do not treat this build as
production-ready Internet multiplayer or as a verified gameplay bridge.

## Changes made

- Compatibility command now returns failure for an unknown game executable.
- Host readiness is emitted only after the socket is listening; launcher waits
  for that event instead of declaring success immediately after process launch.
- Client admission has a 15-second deadline. Save streams have idle timeouts.
- Save request replay tracking is bounded and pruned. Host rechecks invitation
  expiry at admission, including sockets opened before the deadline.
- Diagnostics use an allowlist of scalar fields; nested network payloads,
  credentials, display names, and endpoint addresses are excluded.
- Launcher parses structured helper events, retains a bounded log history,
  fixes Windows argument quoting, hides the long join code in an expander,
  adds keyboard-focus styling and rounded buttons, and permits scrolling.
- Host explicitly selects a save. Joining no longer claims “Ready to play”
  merely because a save download completed. Routine launch no longer runs the
  entire test suite.
- New game-bridge helper reads strictly parsed telemetry, acknowledges fresh
  counters atomically, rejects other sessions and malformed Lua, detects stale
  telemetry, and owns the directory exclusively. The game panel exchanges
  clocks through documented app userdata APIs. Launcher starts this bridge
  with the session and requests graceful helper shutdown.

## Verification

36 Node tests passed, including new bridge acknowledgement, replay/staleness,
exclusive ownership, malformed input, and diagnostic privacy coverage. WPF
launcher compiled as version 0.6.0.0. Visual review was interrupted through

## Open findings and remaining implementation

1. The new bridge transports diagnostic clocks only. It does not replicate
   gameplay, assign companies, intercept native UI actions, or enforce
   deterministic speed. Validate actual userdata serialization and reload
   behavior inside TF3 before extending it to the owned-vehicle command path.
2. A crashed helper can leave bridge.lock behind. Automatic stale-lock recovery
   and recovery UI are still needed. Graceful launcher stop releases it.
3. All players share one encryption key. This is not independent peer/host
   authentication against a malicious invited participant. A standard TLS
   transport with host certificate pinning and separate admission credentials
   is preferable to treating this custom encrypted protocol as production safe.
4. Save contents are hashed before being reopened for transfer. Immutable
   snapshotting is needed to prevent concurrent game saves from invalidating
   transfers. Bind response authentication to each download request to reject
   replay of previously authenticated responses.
5. The model command queue can execute overdue commands and has no complete
   cross-instance pause barrier or desync recovery. Gameplay must stay disabled.
6. Game discovery still assumes the E: installation and derives userdata from
   it. Multiple Steam users, other libraries, and stale staged-mod upgrades
   need a complete selection/update workflow with recoverable backups.
7. Bridge directory selection currently follows the detected save directory;
   custom save/user selections need explicit propagation. Runtime userdata
   root must be confirmed with app.getUserDataFolder.
8. Manifest hashing needs locale-independent ordering, explicit path/content
   boundaries, and rejection of links. Existing peers compare only this mod's
   package, not the complete enabled-mod set in the save.

Next: re-audit the updated TF3 build, validate the diagnostic bridge in a
disposable save, then implement and measure the owned-vehicle request/event
adapter and synchronized scheduling. No two-instance gameplay proof exists.
