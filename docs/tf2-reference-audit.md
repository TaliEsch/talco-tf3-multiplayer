## Important limitations in the reference

The architecture documents known fail-open decode behavior and `docs/KNOWN_ISSUES.md` still lists capture gaps, unsupported commands, pacing/history issues, company-mode crash reports and session-test-pending features. `docs/REPLICATION.md` distinguishes strict capture from post-hoc polling/replay and names cases where an action may run only on the originator. Thus the reference is practical engineering evidence, not proof that every advertised family is safe or that the design transfers to TF3. Its own same-machine determinism result is bounded. Its native hooks are specifically tied to TF2 build 35924.

## Unsafe to transplant to TF3

- Any TF2 address, signature, prologue, calling convention, pointer layout, vtable, command factory/list layout, or assumptions about callback thread, lifetime, and completion behavior.
- TF2 proposal formats, Lua/API calls, command codecs, entity identities, save internals, IPC/file protocol, lobby identity/roster semantics, DLL proxy/load chain, or UI interception details.
- The reference's fail-open decode policy where the TF3 safety contract requires halt on uncertain mutation outcome.
- Claims that same-machine no-input agreement, its scoped script RNG wrapper, or shared seed guarantees cross-machine or whole-world determinism.
- Any assumption that host/client engine player IDs, company wallets, balances or local numeric entity IDs align across instances.

## Actionable TF3 work and unresolved assumptions

1. Continue TF3-specific simulation/command boundary qualification from the exact executable hash and reported candidate call graph; require thread, update, ownership, callback/lifetime, in-memory expected-byte, and teardown evidence.
2. Establish a two-instance no-input baseline at common update counts with explicit coverage for town growth, economy, topology, vehicles and hidden/RNG state. Record what cannot be read.
3. Implement instance-local logical identities and a supported command inventory before broadening execution; bind every action to the authenticated company's identity and verify native ownership and actual debit.
4. Connect the native observation/control path to the existing coordinator only when an IPC request returns a correlated execution receipt and observed postcondition. Keep remote gameplay disabled until mismatch, disconnect and outcome-unknown paths halt safely.
5. Preserve checkpoint recovery as reload-and-compare, not rollback. Recovery needs a fresh pause/drain and common save verification on every instance.

Unresolved: TF3's exact command families and ownership/economy semantics; whether any reported TF3 candidate is a stable and safe interception/clock boundary; observability of relevant hidden simulation/RNG state; cross-machine deterministic behavior; and real-game execution/recovery evidence. None can be concluded from the TF2 reference.
